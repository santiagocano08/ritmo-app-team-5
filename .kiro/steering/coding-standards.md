# Coding Standards & Global Rules

## 1. Design Principles & Simplicity

- **KISS & YAGNI First:** Implement the simplest solution that satisfies current requirements. Do not introduce premature abstractions, complex design patterns, factories, or intermediate layers for unrequested future scenarios.
- **Pragmatic SOLID:**
  - *Single Responsibility (SRP):* FastAPI routes handle only request/response validation; `services` contain business logic; `repositories` execute SQL. In React, separate data fetching (hooks) from presentation (components).
  - *Dependency Inversion:* Inject database connections and configurations via FastAPI `Depends()` rather than instantiating global clients inside functions.
- **Balanced DRY:** Avoid duplicating business rules or data schemas (use Pydantic + `openapi-ts` as the single source of truth). However, **prefer slight duplication in UI or SQL queries** over creating rigid, hard-to-maintain generic abstractions.

## 2. Change Control & Scope (Anti-Overengineering)

- **Surgical Edits (Minimal Footprint):** Modify only the files strictly required to complete the task. Do not refactor unrelated code, rename out-of-scope variables, or reorganize directories unless explicitly requested.
- **Immutability by Default:** Prefer transforming data by creating new objects/dictionaries rather than mutating state or passed-in arguments in place (especially in React state and Python data pipelines).
- **Bounded Size:** Keep functions and components small and focused on a single task. If a file exceeds ~200–250 lines, consider splitting it by clear responsibility.

## 3. Stack-Specific Rules (`psycopg 3` + FastAPI + React)

- **Strict Parameterized SQL:** Always use `psycopg 3` placeholders (`%s` or `%(name)s`) passing parameters as a tuple or dictionary to `cursor.execute()`. **Never** build queries via string concatenation or f-strings.
- **End-to-End Strong Typing:** Enforce full type hints in Python and strict TypeScript (`strict: true`, no `any`). Map `psycopg` rows directly to Pydantic models using `dict_row` or `class_row`.
- **No Manual Fetching in React Components:** All HTTP requests must go through the autogenerated OpenAPI client and be managed via **TanStack Query** (`useQuery` / `useMutation`). Never use `useEffect` for backend data fetching.

## 4. Comments & Code Cleanliness Policy

- **Self-Documenting Code:** Use clear, descriptive names for variables, functions, and SQL queries so the code reads naturally without extra commentary.
- **What TO Comment:** Only explain the technical **"why"** when dealing with a non-obvious constraint (e.g., a specific PostgreSQL index optimization, a library workaround, or a complex domain rule).
- **What NOT to Comment (Strictly Prohibited):**
  - Do not write comments narrating agent decisions, change history, or explanations of the chosen solution (e.g., `// Changed to fix bug X` or `// Decided to use this pattern because...`). Those belong in commit messages or ADRs.
  - Do not leave commented-out code, debug `print()` / `console.log()` statements, or `TODO`s without an associated ticket.
  - Do not add redundant docstrings that merely restate the function name (e.g., `def get_user(id): """Gets a user by id"""`).
